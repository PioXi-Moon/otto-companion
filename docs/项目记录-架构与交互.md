# Otto 项目记录：架构演进与人机交互

> 这份是结项用的总记录：软件怎么长成现在这样、每一次为什么这么选、
> 踩过哪些坑、哪些验证过、哪些还没验证。

## 零、愿景层：我们在做一件什么事

### 一句话

> **别的 AI 在等你开口，Otto 在过自己的日子。**

### 三代交互

| 代 | 范式 | 用户的动作 | 产品的假设 |
|---|---|---|---|
| 第一代 | 指令式（App / GUI） | 操作它 | 功能越多越好 |
| 第二代 | 对话式（Chatbot / LLM） | 问它 | 回答越好越好 |
| **第三代** | **存在式（Otto）** | **介入它的日子** | **它越在场，关系越深** |

第三代交互的第一性原理，从"响应"换成"在场"。

一旦承认这一点，产品形态会自己长出来：它要有自己的节奏（摸鱼、打盹、碎碎念），
要有自己的判断（日记），要有自己的边界（按关系解锁），要有自己的未来（线头）。
这些不是功能，是"存在"的必要条件。

### 三个主张

1. **第一个有自己日子的 AI。**
   不是"你不说话它就待机"，是你不说话它也在过。
   已落地：碎碎念、打盹、线头到期主动开口、它自己写的那本日记。

2. **第一个"人格可追溯"的陪伴体。**
   大多数 AI 伴侣的行为是黑箱；Otto 把对你的判断写进日记，
   你能翻开那本账，看到它为什么今天这样对你。

3. **第一个把"摩擦"当资产的关系。**
   没有摩擦的陪伴是客服。它会误解、会嘴硬、会闹别扭，但纠正之后会改。

### 理论命名

**状态驱动的角色交互（State-Driven Character Interaction）**

> 输入不产生回答，输入改变存在状态；行为不是查表，是状态的投影。
>
> **我们不让它做最优解，我们让它做它的解法。**

三层：言语行为 → 存在状态（六维）→ 冲突解算 → 表达意图 → 动作。
详见 [本体与交互模型](本体与交互模型.md)。

### 愿景与现实

| 我们说的 | 现在做到哪 |
|---|---|
| 第一个有自己日子的 AI | 碎碎念、打盹、线头主动开口已跑通；还没有完整日程 |
| 第一个可追溯的人格 | 日记里的判断已能对应到行为；还没做到每条行为都可回指 |
| 把摩擦当资产 | 傲娇/嘴硬/疏离已在动作层体现；"误解—纠正"闭环还没做 |
| 状态驱动交互 | 已实现：六维状态、五组冲突、意图层、调试面板；**意图已成为动作的硬约束**，模型只在意图内挑表达 |

**大话放在愿景，证据放在现实。** 这份记录里，凡是"已经跑通"的都有日志或自检，
凡是"要做成什么"的都不冒充已完成。

## 一、项目是什么

Otto 是一个桌面陪伴机器人。软件先行，硬件后配：电脑里跑它的记忆和人格，
实体机器人负责身体和存在感。

要验证的假设只有一条：

> **关系感来自记忆的连续，而不是回答质量。**

所以第一阶段做的不是完整 App，是一台用来验证这句话的仪器。

## 三、软件架构

```
┌───────────────────────── 电脑 ─────────────────────────┐
│                                                        │
│  桌宠窗口(Electron)        面板窗口(Electron)            │
│  pet.html / pet.js         index.html / app.js          │
│  参数化骨架 + 动作         记忆/日记/关系/工具/测试       │
│        │                        │                      │
│        └──────────┬─────────────┘                      │
│                   ▼                                    │
│           server（Node，7788）                          │
│  对话 / 记忆 / 日记 / 线头 / 人格 / 关系 / 硬件帧        │
│                   │                                    │
│      ┌────────────┼──────────────┐                     │
│      ▼            ▼              ▼                     │
│   SQLite      DeepSeek API    小智服务端(8000/8003)     │
│  data/otto.db                  │                       │
│                                ▼                       │
│                      BLE 硬件桥(7790)                  │
└────────────────────────────────┼───────────────────────┘
                                 ▼
                         Otto Nano（4 舵机 + 蜂鸣器 + 点阵）
```

分层原则：

- **壳**（Electron）只负责窗口、拖拽、缩放、退出，不放业务
- **服务端**放所有"它会记得什么、怎么反应"的逻辑，可单独跑、可测
- **前端**不直接调模型，只消费服务端的流
- **硬件桥**只做协议转换（HTTP ↔ BLE），不掺业务
- **语音层**（小智）只负责唤醒、录音、播放，大脑仍在服务端

## 四、数据模型

| 表 | 存什么 | 关键字段 |
|---|---|---|
| `message` | 对话原文 | role、proactive、interaction_type、source |
| `memory` | 抽取出的记忆 | category（event/user_info/relationship）、来源、可改可删 |
| `diary` | 一天一页 | 印章、版式、道具、正文、卡片、页脚 |
| `open_loop` | 未闭合的线头 | event、due_at、status |
| `timeline` | 关系里程碑 | kind、title、detail |
| `event_log` | 非对话交互 | 摸、拎、碎碎念、主动发起 |
| `relation` | 关系状态 | 了解程度、共同经历、情绪基调 |
| `persona` | 人格 | 五维、描述、锁定时间 |

设计原则：记忆是**三类**（事实/偏好/关系），每条标来源（"你说过的"/"我猜的"），
用户可改可删。它的日记是它自己的，不给改。

## 五、四条主链路

**1. 对话链路**
输入 → 判断互动类型 → 读关系状态 → 召回记忆 → 装配人格 → 流式生成 →
先出动作再出文字 → 结束后异步抽取记忆。

**2. 记忆链路**
对话 → 抽取（事实/偏好/关系）→ 入库 → 召回打分 → 注入下一轮。
关掉记忆注入就是对照组，其余完全一致。

**3. 日记链路**
一天的材料 → 印章（题眼）→ 道具/版式 → 正文 → 卡片 → 页脚 →
规则校验（句长、复述、清点、人称、卡片重复）→ 不过关重写一次。

**4. 语音 → 动作链路**
小智唤醒 → 录音 → ASR → DeepSeek → 选动作 → `otto_react`/`otto_move` →
HTTP 到 7790 → BLE → 固件执行 → 返回 ACK → 回话。

## 六、人机交互设计

### 三档交互强度

| 档位 | 形式 | 注意力成本 |
|---|---|---|
| 零输入 | 它在动、在嘟囔 | 余光即可 |
| 一比特 | 点一下 / 拎起来 | 一个动作 |
| 低频深聊 | 打字 | 最贵，只在真想说话时 |

最贵的一档不该是门面，所以聊天框从第一屏拿掉了。

### 记忆的可视化

记忆在模型里，用户看不见，所以"它记得你"只是一句它自己的声明。
可视化就是把这句话变成用户可以自己验证的东西：一天一页、每天记住几件、
原样的对话流水、只涨不跌的了解程度。

### 期待感

三个机制，全是"让你等"，不是"催你"：

- 卡片今天给，明天才能翻
- 日记按关系深浅逐层解锁，日期直接写在界面上
- 线头记着你的未来，到点它自己来问

### 分寸与归属

日记是它写给自己看的，卡片是它写给你的。读者不同，规矩就不同。
如果所有东西随时可查，它就从"一个有自己世界的东西"退化成一个数据库。

### 可爱要能被关掉

断网时不卖萌、不假装正常；碎碎念有频率上限；同一种情绪不会每句都换。

## 七、验证方法

| 方法 | 验的是什么 |
|---|---|
| 42 项链路自检 | 记忆写入/召回、线头到点、主动发起、埋点、动作名与道具名对齐 |
| A/B 开关 | 关掉记忆注入，其余不变，看召回是否真的消失 |
| 虚拟时钟 | 把"下周四"压缩到几分钟内验证 open loop |
| 日记规则闸门 | "像人话"这种主观要求，转成可算的规则 |
| 动作调试台 | 62 个动作逐个检查，且不写事件、不进记忆 |
| 硬件帧 | 每个动作翻译成四颗舵机角度 + 灯 + 蜂鸣器，可直接给固件 |

通过标准一开始写的是"测试者能主动说出它记得我"，后来改成
**"他说出这句话的时候，我有没有引导过"**——没引导，才算数。

## 八、踩过的坑（都值得写进结项）

| 问题 | 现象 | 根因 / 修复 |
|---|---|---|
| 冒烟测试清空数据 | 测试把正式库的对话和记忆全删了 | 自检第一步是 `/api/dev/reset`，默认又打 7788。改成默认打 7789，指向别处必须显式确认 |
| 日记像复述 | 读完没有任何等待的理由 | 推翻五版，最后定"看见/串联/细节/悬念"四条判据 + 规则闸门 |
| 腮红让整只宠物消失 | 带 blush 的动作一播，桌宠 `display:none` | `.blush{display:none}` 同时命中了 `.otto.blush`，限定到 `.breathe .blush` |
| 页面整块不动 | 面板没有数据、`{{pet}}` 没替换 | `init()` 在模块求值前访问了还没初始化的 `const`（TDZ） |
| 测试面板排版错乱 | 卡片变成横排、按钮挤成一列 | 日记卡片的 `.card` 选择器是全局的，限定到 `.cardwrap .card` |
| 让它走它不动 | 模型调了 `self_otto_move`，只回 true | 设备端 MCP 工具遮蔽了服务器端工具，过滤 `self.otto.*` |
| 它把 JSON 念出来 | "走啦~","otto_move": "fo | `direct_answer` 参数提取只按结尾裁剪，改成在第一个未转义引号处停 |
| 音效不响 | "完成/困惑"没有声音 | 固件只有 BOOT/HAPPY/SAD/ALERT/CLICK，`SUCCESS/ERROR` 不存在 |

## 九、当前边界

**已经确定**：记忆写得进、召得回；时间到会主动来问；关掉记忆后相关表现消失；
42 项自检全过；动作能落到硬件并在 2.9–6.4 秒的组合里完成。

**还不能确定**：人会不会因此对它产生感情。这需要真人连续用几天，
第一阶段验证不到。所以结项时不能说"验证成功"，只能说链路跑通了。

**物理上限**：四个舵机的幅度写死在固件（SWING 25°、BOW 20°、WAVE 22°）。
再大的幅度要改固件重烧，不在软件层解决。

## 十、下一步

1. 本体模型落地：六维状态、冲突对、意图层（见《本体与交互模型》）
2. 找 5–8 人真用几天，看有没有人自己说出"它记得我"
3. 补第一天体验：新用户进来时前面什么都没有，而留不留人恰恰在那一刻决定

## 十一、怎么跑

```powershell
# 桌宠 + 面板（自带服务端）
双击 启动 Otto.bat

# 小智语音链路
双击 启动小智服务端.bat     # 约 60–90 秒加载模型
python scripts\ble_otto_bridge.py   # BLE 硬件桥，7790

# 只起服务端
pnpm start

# 静态自检（不需要服务）
node scripts/smoke.mjs --static
```

目录：`server/` 大脑 · `ui/` 样子 · `electron/` 窗口 · `scripts/` 工具与硬件桥 ·
`firmware/` 固件源码 · `docs/` 文档。
