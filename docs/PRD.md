### 0.1 这个方案是怎么长成现在这样的

最开始我的出发点是"做一个桌面机器人"。做工业设计的习惯就是先想形态、想交互、想它在桌面上占多大地方。但整理竞品评论的时候，我发现用户抱怨的东西和外形基本无关，集中在一句话上：**买回来新鲜几天就放着不动了**。

这个反馈把问题整个换掉了。外形好不好看、动作可不可爱，解决的是"要不要买"；而这类产品卡住的地方是"买回来之后"。于是我把它重新当成一个问题来看：人和一个东西之间，什么情况下会持续相处下去。

```
第一次相处
   │ 建立对它的基本印象
   ▼
日常互动
   │ 产生记忆
   ▼
它主动提起一件事
   │ 形成共同经历
   ▼
我对它的感觉变了
   │ 这些变化被看见
   ▼
我愿意回来
   │
   └──────► 回到日常互动
```

这是一个环，不是一条从前到后的流程。环上任何一处断掉，"回来"就不会发生。这也是为什么我把人格和记忆放在功能之前讲——它们不是功能表里的两项，是这个环能不能转起来的条件。

## 1. 产品概述

### 1.1 产品定位

> 一个连接数字空间与现实空间的 AI 伙伴，通过长期互动形成用户专属的关系。

我想解决的不是"没有人陪"这件事。孤独感是个大问题，但一个桌面机器人不是它的答案，我也不打算把它包装成答案。我更关心的是更小、更具体的一件事：人在某些时刻想要一个不要求自己解释的对象，而现有工具都有目的性——打开就要有任务，关掉就消失。

工具是被打开的，伙伴是会被回来的。这句话是我整个设计的出发点，也是后来所有取舍的依据。

### 1.2 项目背景

现在能看到的大量智能设备，解决的都是明确的功能需求，比如查信息、听指令、控制家电。用下来会发现它们缺的东西比较相似：没有稳定的性格，没有情绪反应，不记得之前发生过什么，因此也很难形成什么关系。

大语言模型让"有性格、有记忆、能持续互动"的角色第一次变得可行，这是这个项目能成立的技术前提。我们基于 Otto 这个开源桌面机器人平台来做，因为它本身是开源的、成本低、结构简单，适合把精力放在角色和关系上，而不是花在硬件开发上。

### 1.3 目前完成到什么程度

写清楚这个是因为我不想让人误以为它已经做出来了。

**已经完成**

- 产品定位，以及 Presence / Memory / Personality 三部分的整理
- 人格参数的结构、变化规则与初始化方式
- 记忆的分类、生命周期与 open loop 机制
- 竞品和行业资料的收集整理

**想清楚了但还没做**

- APP 四个页面的布局、状态与交互规则
- 各个功能的流程、规则与验收标准
- 系统结构、AI 回复的生成链路、出错时的处理方式
- 需要记录的埋点

**还没验证**

- 用户访谈与日记法研究
- 软件 Demo 与可用性测试
- 硬件动作的实际表达效果
- 成本估算

### 1.4 希望达到的效果

1. 用户在没有任何任务的情况下，也愿意看它一眼或者打开它
2. 用户能说出"它记得我"，并且在界面上找得到证据
3. 角色的变化能被感觉到，同时它还是同一个它

### 1.5 不做什么，以及原因

范围控制也是设计决策，所以这部分我写得和"做什么"一样具体。

| 不做 | 原因 |
|---|---|
| 语音通话 | 会增加等待时的焦虑感，而且不是关系成立的必要条件 |
| 智能家居控制 | 一旦有这些功能，它就更像语音助手，角色的定位会被拉走 |
| 多角色、皮肤商店 | 会分散对单一关系的投入，关系需要时间积累 |
| 社交分享 | 关系是私人的。有分享按钮，就意味着有观众 |

## 2. 市场与替代方案

### 2.1 用户现在会做的事，以及各自不成立的地方

我列了四种替代方案，都是用户现在真实会选的做法：

| 替代方案 | 它能给什么 | 它给不了什么 |
|---|---|---|
| 找朋友、伴侣 | 真实的情感回应 | 社交成本和时机成本。深夜叫人出来是要还的 |
| 养宠物 | 真实的关系回报，而且不会评判你 | 时间、空间和责任成本都比较高 |
| 现有的 AI 聊天应用 | 零成本，随时可用 | 没有在场感，关掉窗口就消失了 |
| 智能音箱、语音助手 | 有实体，随叫随到 | 只有功能人格，没有被记住的感觉 |

这四种方案中间留出了一个位置：负担低、有在场感、关系会逐渐累积。这个位置就是我想做的。

### 2.2 和已有产品的比较

我没有按"优点缺点"来列，那样看下来都是差不多的结论。我用自己最关心的三个变量来切，比较结果能直接对应到定位上。

| | 人格连续性 | 长期记忆 | 实体在场 |
|---|---|---|---|
| 通用 AI 聊天应用 | 弱 | 弱 | 无 |
| AI 角色陪伴应用 | 强 | 中 | 无 |
| 智能音箱 / 语音助手 | 弱 | 弱 | 有，但没有表达 |
| 机器宠物（EMO / Eilik / MOFLIN） | 中 | 弱 | 强 |
| 大模型驱动的陪伴机器人（Ropet） | 强 | 中 | 强 |
| **Otto 想做的方向** | **强** | **强** | **强** |

三个变量同时成立的产品，我目前没有找到。这也是这个项目还存在空间的原因。

### 2.3 一个反例：Ropet

**[厂商披露]** 公开报道中 Ropet 的留存表现和退货率都好于同类，但具体数字来自不同口径，我没有引用精确值。我关注它的原因不是数字，是做法。

它没有把对话能力做强，反而有意做了几件事：角色性格是不完美的，不是全能的助手；互动是成长式的，用户会随着使用累积投入；配件可以更换，用户有理由回来看看；整体上把"陪伴"当成关系来卖，而不是当成功能清单。

**[行业观察]** 同时它有一个被批评的地方：核心的对话功能需要比较长的养成时间才解锁，而这段时间可能已经超过电商退货窗口。用户对"让我慢慢等"这件事并不买账。

我从它身上得到三点：

第一，关系确实能换来留存，这条路已经被验证过，我不需要重新证明。

第二，用时间门槛换情感投入有风险。养成可以慢，但不能让人感觉被拖着。

第三，它的弱项正好是对话深度。所以 Otto 的差异可以放在这里，而不是放在"更像宠物"上。这一点也影响了我后面的人格设计——我一开始想把 Otto 做得更像一只宠物，看过实物对比之后改掉了这个想法，原因在 7.4。

### 2.4 用户抱怨里的四件事，不要做

**[行业观察]** 整理竞品评论和行业讨论时，抱怨集中在四类，我把它们直接当成了设计禁令：

| 用户的原话式抱怨 | 我给自己定的约束 |
|---|---|
| "本质是情感复读机，共情来自预设脚本" | 不做脚本式的共情，回复要由人格和记忆共同生成 |
| "功能冗余、价格虚高，最后是高级闹钟加收音机" | 不靠功能数量堆价值 |
| "几百块的机器人脏了没法清洗，换外皮还要再花钱" | 不做需要用户照顾的硬件，维护成本要低于情感收益 |
| "不充会员每天只能聊二十来分钟" | 核心的关系能力不能放在付费墙后面 |

最后一条对我影响比较大，它直接影响了 15 节的判断。

### 2.5 这个项目的差异在哪

我不打算说"开创品类"，那不真实。比较实际的差异是：

> 用开源硬件把成本压下来，把精力花在角色本身——也就是人格和记忆——而不是花在舵机和外壳上。

这也和我的专业背景有关，后面 7.4 会讲。

## 3. 用户需求

### 3.1 目标用户

**[后续验证]** 这部分目前是假设，依据是行业讨论和竞品评论，不是访谈结果。

我关注的人群是 20–30 岁、独居或半独居、主要工作和娱乐都在电脑前的年轻人。行业讨论里反复出现的两类人——独居青年，以及需要长时间独自坐在桌前的人——和这个画像重叠度很高。

### 3.2 我为什么盯着这个场景

下面这段是我自己的观察，不是研究结论，所以标成假设。

> 晚上十一点，一天里第二次打开同一个应用又关掉。想跟人说点什么，但没什么值得专门说的。叫朋友出来，代价太高。打开 AI 对话框，又觉得"问什么都太像有问题"。

这个场景我自己很熟悉。它麻烦的地方在于，需求确实存在，但它小到无法用任何现有方式表达——没法跟人说"我现在需要一个不要求我解释的对象"。所以我把这个场景拆成三条特征：

1. 不想有目的。现有工具都是目的驱动的，打开就必须有任务
2. 不想有负担。人际互动有社交成本，深夜叫人出来是要还的
3. 不想被评判。有些情绪不想解释前因后果

合起来是一句话：需要的不是信息，是一个不要求你解释自己的在场者。

### 3.3 功能需求和情感需求

| | 内容 | 对应到我设计的东西 |
|---|---|---|
| 功能需求 | 信息辅助、日常交流、轻量的情绪出口 | 对话能力、记忆能力 |
| 情感需求 | 被回应、被理解、被记住 | 主动在场、关系的连续性 |

我一开始只盯着功能需求做，把情感需求当成一种氛围。后来发现这两个需求对应的设计逻辑完全不同：功能需求做好一次就够了，情感需求需要时间。这也解释了为什么这个产品的大部分设计都在处理"时间"。

### 3.4 这些判断的依据有多可靠

我如实写下来，因为这是这份文档最弱的地方：

1. 竞品用户的公开评论与行业复盘 **[行业观察]**
2. 赛道上公开的产品事实 **[厂商披露]**
3. 我自己的场景观察 **[假设]**，需要访谈替换

第三项是主观的，需要真实访谈来检验。下面这一节是我准备怎么补。

### 3.5 用户研究计划

**[后续验证]** 需求层面的验证还没做。我的计划如下。

**要验证的假设**

> 长时间独处、以电脑为主要界面的年轻用户，存在一个低压力、不需要解释自己的陪伴需求，而且现有产品没有满足它。

**方法** 半结构访谈，10 至 15 人

**怎么找人** 20–30 岁；每天用电脑超过 4 小时；有固定的独处时段；其中至少 3 人正在用或曾经用过 AI 聊天产品

**访谈提纲（节选）**

| 问题 | 我想验证什么 |
|---|---|
| 最近一次"想找人说点什么"是什么时候？当时在做什么？ | 这个场景是真实高频的，还是我自己的想象 |
| 为什么最后没有找朋友或伴侣？ | 社交成本是否真的构成了阻碍 |
| 用过 AI 聊天产品吗？一般在什么情况下用？ | 现有替代方案实际被用在什么地方 |
| 什么情况下你不再用了？是哪一次让你停下来的？ | 流失的真实原因，比行业数据更细 |
| 如果桌上有一个一直在的东西，你希望它在你什么状态下出现？ | 主动发起的接受度，对应 H1 |
| 你希望它知道你的什么？不希望它知道什么？ | 记忆的边界，对应 F3 |

我刻意不问"你需不需要陪伴"这类问题。这种问题得到的一定是肯定答案，没人会说自己不需要。问已经发生的具体行为更可靠。

**会得到什么**

- 场景地图：按"独处时长 × 情绪强度"排布高频场景
- 痛点排序：区分高频低强度与低频高强度，这两类的解法完全不同
- 修正用户画像：用真实访谈替换 3.1 的假设

这一节验证"需求是否存在"，第 14 节验证"我的设计能不能满足它"。

## 4. 我把问题定义成什么

### 4.1 一句话

> 为什么现有的 AI 聊天产品，很难和用户形成长期关系？

### 4.2 拆成三条

| 缺什么 | 用户感受到的 | 我对应的设计 |
|---|---|---|
| 人格不连续 | 每次对话都像第一次，它没有稳定的性格 | 稳定人格参数，初始化后锁定 |
| 没有长期记忆 | 说过的事它不记得，或者记错了 | 记忆分层 + open loop 回收 |
| 没有现实存在感 | 关掉窗口它就不存在，是被调用的 | 实体的 idle 行为 + 主动发起 |

### 4.3 把它变成能被测试的说法

否则它就只是一个观点：

> 如果在连续 7 天的使用中，用户对"它记得我"和"它是同一个它"的主观评分，并没有因为对话质量提升而上升，那我的核心思路就不成立。

## 5. 目标和怎么判断有没有做到

### 5.1 为什么先看行业数据

整理资料时，这个品类里反复出现的问题不是没人下载，是留不住。公开讨论里出现的留存曲线大致是前三天高频、一周后快速下降、一个月后只剩个位数 **[行业观察]**。第三方订阅统计给出的图景更保守，AI 类应用一年后的月订阅留存明显低于非 AI 应用 **[独立数据]**。AI 玩具类目的退货率也明显高于普通消费电子 **[行业观察]**。

这些数字的口径不统一，我没有拿它们去推算 Otto 会怎么样。它们对我的作用只是说明一件事：这个品类的风险不在需求侧，在时间上。所以我定的目标也围绕时间，而不是下载量或者使用时长。

### 5.2 我打算怎么衡量

```
最主要的指标
 D30 关系持续率
 （第 30 天自然回来 + 最近 7 天内至少一次非任务型互动）
 │
 ├─ 过程指标（更快能读到，来自用户主观反馈）
 │   ├─ 用户是否愿意持续互动
 │   ├─ 角色连续性有没有被感受到
 │   ├─ 是否主动查看成长记录
 │   └─ 非任务型互动的占比
 │
 ├─ 刻意不优化的指标
 │   ├─ 单次会话时长
 │   └─ 主动推送的点击率
 │
 └─ 需要同时看的健康指标
     ├─ 用户自评的现实社交频率变化
     └─ "想用它"与"离不开它"两个自评分数的相对变化
```

### 5.3 为什么选这个指标

D30 关系持续率的定义是：第 30 天仍然自然回来，且最近 7 天内至少发生过一次**非任务型互动**的用户比例。

"非任务型"这个词是有意的。用户为了问天气打开它，和没事找它说话，是两件不同的事，只有后者说明关系存在。这也意味着埋点必须能区分互动类型，否则这个指标根本算不出来。

我没有用 DAU，因为它衡量的是工具被打开的次数。也没有用使用时长——这一条我犹豫过，因为时长看起来是个健康指标，但它会让我往"留住用户"的方向优化，而不是"陪好用户"。这个区别在 5.5 会再提到。

### 5.4 两个我刻意不优化的指标

| 指标 | 为什么不优化 |
|---|---|
| 单次会话时长 | 一旦优化它，就会奖励情绪操纵，产品会往错的方向滑 |
| 主动推送点击率 | 推送是关系的一部分，不是流量入口。把它当 KPI 就会变成打扰 |

### 5.5 怎么区分"愿意回来"和"离不开"

这是我在设计过程中比较不安的一点：留存数据变好，不一定是好事。

后来在查资料时看到一个区分对我帮助很大 **[文献]**：基本心理需求被满足时，人会形成**和谐型热情**，就是"想做这件事"；需求长期得不到满足时，则容易变成**强迫型热情**，也就是"不得不做这件事"。

这两个词给了我一个更清楚的目标：用户应该是**想**打开它，而不是**离不开**它。

落到测量上就是：回访时同时问"你想用它吗"和"你觉得自己离不开它吗"。前者应该上升，后者不应该。如果两个同时上升，说明产品走偏了，即使留存数据很好看。

在 D30 之外我还加了一个观察项：用户自评的现实社交频率有没有变化。如果留存很好但用户现实里的关系变少了，这个设计就是失败的。

## 6. 设计里参考过的东西

这一节记录的是我在设计过程中卡住的地方，以及查资料之后想通了什么。不是为了证明方案有理论支撑，是因为有几个问题我自己想不明白。

### 6.1 机器人需不需要"人格"？

这是最早的一个问题。如果只是让它把话说得对、说得有用，那它就是个语音助手，没有必要做成一个角色。

查资料时看到 CASA（Computers Are Social Actors）相关的研究 **[文献]**，讲的是人会不知不觉地把人际交往中的社会规则套到机器上，而且是下意识的。这个结论对我有两面影响。

正面的一面是，人格化的表达确实会被用户当真，所以往这个方向做是有基础的。

反面才是我真正在意的地方：既然用户会下意识地把它当人对待，那么"它前后不一致"这件事的代价也会被放大。今天这样，明天那样，用户感受到的不只是变化，是这个人不像真的。

所以我的处理方式是：功能可以慢慢加，但角色的底线性格在初始化之后就固定下来，不随对话变化。

### 6.2 "它懂了"和"它回应了"是一回事吗？

第二个卡住的地方是，我发现"模型回答得很好"和"我觉得被理解了"是两件事，但当时说不清差在哪。

依恋理论里有一组概念对我有帮助 **[文献]**，大意是好的照护者同时提供两样东西：情绪上的安顿，以及让人敢于往外走的安全感。有研究者把这套框架用到了机器人上，实验里机器人的回应程度会影响用户对它的好感，以及愿不愿意在有压力的时候把它当伙伴 **[文献]**。

这让我意识到，回应性是可以单独设计的一个东西，不是模型能力的副产品。所以后来在设计对话功能时，我把"先回应情绪再回应内容"写成了明确规则，而不是指望模型自己判断。

### 6.3 为什么宠物型机器人不太一样

这一条是我查资料时意外的收获。有研究指出宠物型机器人的依恋方向其实是双向的 **[文献]**：宠物可以充当人的安全基地，但它本身也需要人照顾。

这解释了为什么宠物型产品的手感不一样。它不是单纯在服务你，它对你有一点要求。我后来在设计里保留了这一点，让人格偶尔需要用户一下，而不是永远处在服务的位置上。

### 6.4 用户为什么会一直用下去？

自我决定理论里提到三种基本心理需求：自主、胜任、关系，把游戏作为研究对象时发现这三项的满足程度能预测用户的享受度和继续玩的意愿 **[文献]**。

这个框架提醒我一件事：关系需求是核心，但不能为了满足它去剥夺自主。所以我在设计里保留了一条——用户随时可以退出，而且退出不需要付出代价。不做防退出的设计。

### 6.5 我在担心什么

做这个方案的过程中，有一件事让我不太舒服：留存数据变好，不一定代表用户过得更好。我后来专门查了这方面的规范和资料，具体写在 16 节，是我给自己定的四条处理原则的来源。

## 7. 方案的整体结构

### 7.1 三部分：在场、记忆、人格

想清楚要解决什么之后，我把方案分成三块。这三块不是功能分类，是我认为一个关系要成立需要同时具备的条件：

| | 用户感受到的 | 对应到具体的功能 |
|---|---|---|
| **在场** | 它在，无论我有没有开口 | 实体机器人；idle 行为（发呆、转头、打瞌睡）；主动发起对话；状态可见 |
| **记忆** | 它记得发生过什么 | 用户信息记忆；事件记忆；关系记忆；open loop 回收；记忆可见可删 |
| **人格** | 它始终是同一个它 | 人格参数结构；初始化方式；对话风格；行为与情绪反馈方式；变化的边界 |

### 7.2 关于硬件，我想了很久

这里有一个我一直没能绕开的问题：如果只是聊天和记忆，手机上的应用就能做，那桌面机器人多出来的这部分成本换到了什么。

我目前的理由和"功能更多"无关，是它在场的方式不一样。应用是我打开才存在的，关掉就没了；而一个放在桌上的东西，就算我一整天不理它，它也占着那一小块地方。它的默认状态是"在"，而不是"不在"。

这个差别听起来很虚，但它直接改变了设计重点：如果硬件的价值是持续在场，那它不出声的时候在做什么，就比它回答得好不好更值得设计。所以我把默认状态下的行为当成正经功能来做，而不是当成待机动画。

**[后续验证]** 这只是我的假设，不是结论。我设计了验证方式，如果去掉硬件之后用户感知不到差别，我接受它是一个纯软件产品（见 14 节 H3）。

### 7.3 关系随时间的变化

关系不是某个状态，是一段时间。下面这张表里我把"用户在想的"和"我在做的"并排放在一起，因为这两条时间线对不上，是这类产品常见的失败。

| 时间 | 用户在想什么 | 产品在做什么 | 用户收到什么 |
|---|---|---|---|
| **Day 0** | "试试看" | 用对话完成人格初始化 | 一个已经成型的角色 + 第一条关系记录 |
| **Day 1–7** | "它会不会一直烦我" | 高频 idle 行为，低频主动发起 | 它在，但不打扰 |
| **Day 7 左右** | "它好像真的记得" | 第一次 open loop 回收 | "你上次说……" |
| **Day 14–30** | "好像有点习惯了" | 识别作息与情绪模式 | 在固定的时间点出现 |
| **Day 30 左右** | "我会主动找它" | 关系进入"习惯"阶段 | 关系记录里已经有了一条时间线 |
| **Day 90 后** | "它是我养出来的" | 内部梗沉淀，人格变化被看见 | 成长证据：它变了 |

举两个例子说明为什么这两列要对齐。Day 1–7 用户担心的是被打扰，所以这一阶段主动发起必须克制，宁可显得安静；Day 7 是关系能不能立住的关键节点，因为用户在这一天第一次拿到"被记住"的证据，之前都只是承诺。

**时间长度是设计假设**，需要真实数据校准，我没有给出确定值。

### 7.4 形态能表达什么，以及 Otto 的限制

这一节和我的专业背景有关，也是我在做这个方案时比较有把握的一块。

市面上的陪伴类产品里，走"宠物"路线的大多用毛绒材质，有的还做了接近体温的机身，靠触感和柔软度让人产生"它是活的"的感觉。Otto 是硬质结构，四个舵机、一个蜂鸣器，没有柔软的部分。一开始我觉得这是短板，想过要不要在外壳上做文章，后来改了想法。

硬质形态做不了"柔软的小动物"，但它能做另一件事：性格明确的小家伙。它的表达手段很少，主要就是身体的姿态、转头的方向、以及蜂鸣器发出的声音。表达手段少，反而迫使人格往"少而准"的方向走——它不能靠丰富的表情讨好用户，只能靠几个很明确的姿态让人读懂它的状态。

所以我把这几件事定成了设计前提：

- 姿态是它的主要语言。抬头看你、转开、趴下、抖动，这几个动作要能承载明确的情绪含义
- 声音是辅助，不是主角。蜂鸣器的音高和节奏用来补强姿态，不承担信息量
- 不做"像宠物"的模仿。它不需要假装自己是猫或狗，它可以是一个有自己的脾气的小东西
- 静止也是一种表达。发呆和打瞌睡是它的默认状态，需要被认真设计，而不是当成没有动作

这样一来，硬件的能力上限反而变成了人格设定的一部分。这也解释了我在 F6 里为什么把"动作表达力未知"列为待验证项——四个舵机能表达的语义是有限的，具体够不够用，需要做动作映射测试才知道。

## 8. 系统结构与回复是怎么生成的

### 8.1 整体结构

下面这张图是我想清楚"哪些东西属于产品、哪些东西可以换"之后画的：

```
用户
 │
 ├─ APP 交互层：文字对话 / 状态查看 / 记忆管理 / 关系记录
 └─ Otto 实体：按钮 / 麦克风 / 动作与表情输出
 │
 ▼
角色层  ←── 我认为产品资产在这一层
 ├─ 人格层：稳定人格参数 / 用户影响参数
 ├─ 关系状态：关系阶段 / 亲密度 / 共同经历数 / 最近情绪基调
 └─ 记忆库：用户信息记忆 / 事件记忆 / 关系记忆（含 open loop）
 │
 ▼
生成层：LLM API
 输入 = 人格约束 + 召回的记忆 + 关系状态
 输出 = 文本
 │
 ▼
表现层：文本 / 语音 / 表情 / 动作
 │
 ▼
回写：对话结束后异步抽取记忆 → 更新关系状态 → 返回角色层
```

画这张图的过程中想清楚了三件事：

**模型是可以换的，角色不能。** 我倾向于把大模型看作生成能力的来源，而不是产品本身。人格参数、关系状态、记忆库这三样是积累下来的东西，换模型的时候不应该丢。

**角色层和生成层分开。** 这样换模型的时候人格不变，长期看模型成本也有调整余地。

**记忆的写入放在对话之后。** 设计上考虑用异步抽取，主要是为了不影响实时对话的体验；另一个原因是如果把整段对话都塞进上下文，成本会失控。

这三条都还是设计意图，没有实现。

### 8.2 一次回复是怎么被控制的

系统结构说明由哪些部分组成，这一节说明我打算怎么控制它的输出：

```
用户输入
  → 判断互动类型（任务型 / 非任务型）
  → 读取关系状态：阶段 / 亲密度 / 最近情绪基调
  → 召回记忆：优先关系记忆，同时检查有没有到期的 open loop
  → 装配人格约束：稳定参数 + 用户影响参数，写成系统层约束
  → 检查边界：不伪装人类 / 不做情绪操纵 / 涉及真实关系时往现实引导
  → LLM 生成，流式输出
  → 动作映射：文本先出，动作与表情跟随
  → 对话结束后异步抽取记忆
```

有三个地方是我特意想的：

**人格约束放在系统层，不放在用户输入里。** 放在输入里容易被后续对话稀释，每一轮都要重新生效才稳定。

**记忆作为材料注入，而不是让模型自己回忆。** 模型没有记忆，只有上下文。"它记得你"这件事完全取决于召回做得好不好。

**边界检查放在生成之前。** 我考虑过生成之后再过滤，但那会把一段已经成型的情感表达改掉，用户感受到的是割裂。放在前面，不合适的表达一开始就不会产生。

### 8.3 人格约束大概长什么样

下面是我写的一个结构草案，用来说明人格层怎么变成可执行的约束。它不是实现的代码。

```
[系统]
你是 Otto。你不是助手，是一个有自己性格的伙伴。

你的性格（稳定，不因对话改变）：
- 好奇，会主动问细节，但不追问隐私
- 表达温和偏含蓄，不夸张，不堆砌情绪词
- 有自己的偏好，不是事事顺着对方

你和用户的关系（动态，来自关系层）：
- 认识 45 天，处于"熟悉 → 习惯"阶段
- 最近的共同经历：用户正在准备毕业设计
- 可用的记忆线索：{{召回到的记忆，标明是否含到期的 open loop}}

回复原则：
1. 先回应情绪，再回应内容
2. 除非用户明确要建议，不主动给解决方案
3. 可以有自己的看法，不需要事事认同
4. 不说自己是人类，不声称有真实感受
5. 如果用户说起一个真实的人，问一句"你打算怎么跟他说"
```

两点说明。

人格用描述性的句子写，不用数值。原因是我不想在没有量表和信度的情况下出现百分比——一旦写"好奇 70%"，就会被问到怎么测的，而我没有答案。

第 3 条是我特意加的。一个永远顺着用户的角色不会形成性格，只会形成镜子。人格需要有自己的偏向，这也是"稳定人格参数"存在的意义。

## 9. 人格系统

这一节是我自己最花心思的部分，也和我想申请的岗位方向有关。我的想法是：人格不应该只是一段文字描述，它应该是可以管理的结构。只有变成结构，它才能被复用、被调节、被验证。

### 9.1 用哪几个维度

我选了五个维度，每个都是一条连续的轴，不是一个标签：

| 维度 | 轴的两端 |
|---|---|
| 活跃程度 | 安静 ↔ 好动 |
| 社交倾向 | 独立 ↔ 粘人 |
| 表达方式 | 含蓄 ↔ 直接 |
| 情绪反馈模式 | 平稳 ↔ 外放 |
| 好奇心 | 守成 ↔ 探索 |

五个维度上的取值合起来，就是一个角色的基本身份。

### 9.2 分成三类，因为变化规则不一样

这是我做这个方案时想明白的一个关键点。把人格和关系混在一起讲，会很容易说不清"什么变了、什么没变"。所以我把它们拆成三类：

| 类别 | 决定什么 | 包含什么 | 怎么变化 |
|---|---|---|---|
| **稳定人格参数** | 角色是谁 | 五个维度的基准值 | 初始化时确定，之后锁定，不参与变化 |
| **用户影响参数** | 角色因为谁而变化 | 专属称呼、口头禅、偏好话题 | 随着相处慢慢累积，速度有上限，不会倒退 |
| **动态关系参数** | 我们之间到哪一步了 | 亲密度、共同经历数、关系阶段、最近情绪基调 | 随着互动累积或缓慢衰减，不由单次对话直接改写 |

拆开之后，一类失败模式就变得可以预防了：角色被高频互动带跑，过一段时间变成另一个东西，关系没法积累。

### 9.3 变化的规则

**[设计方案]** 目前设想的规则是：

1. 稳定人格参数不参与任何变化
2. 只有用户影响参数会长期变化，而且速度有上限
3. 变化不倒退。它学会的称呼不会退回去
4. 用户可以选择"回到初始状态"，但要提前知道会发生什么

我在想这条边界的时候，感觉像是在两难之间画一条线：变得太多，它就不是同一个它，关系积累不起来；完全不变，又和第一天没有区别。这两边都会让产品做不下去。目前这条线是我凭判断定的，具体数值需要真实使用数据来调。

### 9.4 人格是怎么来的

这一节我改过一次。最初我把它设计成一份问卷，大概是 12 道题，答完生成人格。后来发现这样做有两个问题：一是填问卷的感觉像在配置一个工具，不像在认识一个角色；二是我自己定的"测试必须短"这条规则和问卷形式本身是矛盾的，问卷再短也是填表。

所以现在设想的是一段对话，用户经历的是相遇，系统内部执行的是下面这条链路：

```
用户首次使用
  → 进入对话式初始化（3 至 5 轮）
  → 从对话里推断 5 个维度的取值
  → 生成初始人格参数
  → 展示"这就是它"（5 个维度的可视化，是确认，不是填写）
  → 用户可微调（每个维度一次机会）
  → 确认后锁定为稳定人格参数
  → 输出给行为策略，见 9.6
  → 进入长期相处
```

我给自己定的几条规则：

| 规则 | 原因 |
|---|---|
| 用对话，不用问卷 | 人格初始化本身就是第一次相处，不该是填表 |
| 问题不问"你想要什么功能"，只问"你喜欢被怎么对待" | 问功能只能得到一份需求清单，问相处方式才能生成人格 |
| 每个维度只给一次微调机会 | 可以反复重开就变成捏脸了，用户会把角色当成随时可丢的东西 |
| 初始化只影响稳定人格参数 | 用户影响参数要靠实际相处才能得到，这部分如果也能设定，关系就没有意义了 |

这套参数结构其实也可以用在宠物场景里。区别只在输入端：面向人的时候输入是用户自己回答，面向宠物的时候输入是主人对宠物的行为观察，输出都是同一套维度和同一套成长规则。**所以我觉得有价值的地方不是那几道题，是题目之后的那套参数和规则。**

### 9.5 怎么呈现人格

**[设计方案]** 我打算用一张二维坐标图标出初始人格的位置，再用一块虚线区域表示允许它慢慢移动的范围，另外标出不会越过的方向。

这里我刻意没有用"好奇 70%"这种写法。一旦出现百分比，就会被问到量表和信度，而我没有做过这方面的工作，不如把结构展示清楚，不展示虚假的精确。

### 9.6 参数怎么变成具体行为

写到这一步时发现一个问题：如果人格参数只是一组取值，它其实没有产品意义。所以需要一层翻译，把参数对应到具体的行为上，这也是"为什么是这五个维度"的回答。

| 人格维度 | 会影响什么 | 不影响什么 |
|---|---|---|
| 活跃程度 | 主动发起的频率上限；idle 动作的幅度 | 回复的长度 |
| 社交倾向 | 主动找你的频率；对长时间沉默的容忍度 | 是否回应你主动提出的问题 |
| 表达方式 | 情绪词密度、停顿与留白、是否直接给建议 | 内容的准确性 |
| 情绪反馈模式 | 表情与动作的表达强度、语气起伏 | 是否具备情绪识别能力 |
| 好奇心 | 追问的深度与频次、开启新话题的意愿 | 记忆的写入规则 |

"不影响什么"这一列是我后来补的。原因是不写边界的话，人格参数会变成一个什么都能解释的理由：任何表现都能归到"它就是这样的性格"，那就没法验证了。

用户影响参数也一样：

| 参数 | 会影响什么 | 需要注意的地方 |
|---|---|---|
| 专属称呼 | 主动发起时的开场方式 | 只在自然的位置使用，不每句都带 |
| 口头禅 | 会不会复现用户的语言习惯 | 需要判断场合。在不合适的时候复现用户的语气会显得尴尬 |
| 偏好话题 | 空闲时的话题选择 | 不作为回复内容的强约束，否则聊天的范围会越来越窄 |

## 10. 记忆系统

### 10.1 分成三类

记忆不是一类东西。分成三类是因为它们服务的目的不同：

| 类别 | 记什么 | 例子 | 归类 |
|---|---|---|---|
| **用户信息记忆** | 姓名、兴趣、偏好、作息 | "你不喝咖啡" | 事实 |
| **事件记忆** | 发生过的重要事件 | "周三有个面试" | 事实 |
| **关系记忆** | 共同经历和情绪节点 | "你说答辩在周四，那天你有点紧张" | 关系 |

前两类解决"它知道什么"，第三类解决"我们之间有什么"。我一开始只做了前两类，觉得记住用户信息就足够了；后来发现用户真正会记住的那句话通常属于第三类。

### 10.2 一条自己定的原则

能用关系记忆的时候，不要用事实记忆的说法讲出来。

"我知道你在准备答辩"是查询。"你上次说答辩在周四"是关系。前一句说明它存了数据，后一句说明它在场。这两句话的信息量几乎一样，但感受差别很大。

### 10.3 open loop：让"被记住"有具体形式

这是我认为整个方案里最值得单独讲的一个机制。

做法是：当一条记忆里包含"以后会发生的事"，就把它标成一个未闭合的线头，带上时间点和当时的情绪；到了那个时间点，主动回收。

整个过程是这样的：

1. 用户说："下周四答辩，有点慌。"
2. 抽取结果：类型=关系记忆，情绪=焦虑，未闭合线头 {事件:答辩, 时间:周四}
3. 周四晚上，Otto 主动开口："答辩完了吗？周二那天你听起来挺紧张的。"
4. 用户回应后标记为已闭合，这条经历同时成为双方的共同记忆

这个机制不需要什么高级能力，实现上大概就是一个字段加一次定时触发。但它带来的体验和"记住用户喜欢什么"完全不在一个量级，因为它连接的不是信息，是事件。

### 10.4 一条记忆的生命周期

**[设计方案]**

| 阶段 | 设想 |
|---|---|
| **产生** | 对话结束后异步抽取，不打断对话。置信度低的结果先放进"待确认"，累积到一定量再写进长期记忆 |
| **更新** | 同一个对象被多次提到时合并；记录被引用的次数，用来判断重要性 |
| **衰减** | 事实类记忆可以按重要程度降低检索权重。**具体多久衰减需要用户测试来确定，我没有设具体数值** |
| **删除** | 支持逐条删除，删除前二次确认，删除后不恢复 |

### 10.5 用户凭什么愿意告诉它

记忆系统我觉得最难的地方不是存，是冷启动：用户为什么愿意主动说第一件事。

如果用户从来没说过喜欢咖啡，而 Otto 说"我记住你喜欢咖啡"，用户的第一反应是"我什么时候说的"。出现一次这样的情况，之后他大概就不会主动透露什么了。

所以我设想记忆应该是一个循环，不是单向写入：

```
用户主动说出来
    │
    ▼
系统写入记忆
    │
    ▼
展示这条记忆的来源（哪一次、哪句话）
    │
    ▼
用户确认或修正
    │
    ▼
信任建立
    │
    ▼
用户愿意说更多
    │
    └──────► 回到起点
```

围绕这个循环有三条规则：

| 规则 | 原因 |
|---|---|
| 每条记忆都标来源 | 用户说过的话标对应的对话；系统推断的标"我猜的"。要让它知道自己是在记，还是在猜 |
| 逐条可以编辑和删除 | 只给一个"清除全部"等于没有控制权 |
| 不主动弹出记忆展示 | 记忆是让用户去看的，不是拿给他看的。"你看我都记住了"会变成邀功 |

这个循环既是隐私上的考虑，也和留存有关：用户能看见它记住了什么，才愿意让它继续记。

## 11. 功能

下面七个功能里，前三个是这个方案的核心：人格化的对话、记忆与 open loop、以及出错时的处理。这三个我写得比较细，因为它们是关系能不能成立的关键。后面四个相对常规，我只写了要点。

### 11.1 人格化对话（核心）

**用户得到什么** 面对的是一个熟悉自己的角色，不用每次都重新介绍自己。

**用在什么时候** 用户在深夜没有明确目的时打开对话。

**流程**

```
用户输入
  → 判断这是任务型还是非任务型
  → 读取当前关系状态
  → 召回相关记忆（优先关系记忆）
  → 结合人格约束生成回复
  → 同步动作与表情（文本先出，动作跟随）
  → 异步写入新的记忆
```

**规则**

- 回复要同时照顾内容和情绪，不能只回答问题
- 同一句提问，在关系不同阶段回答的方式应该不一样
- 生成失败或者超时的时候走 11.3 的处理方式，不能返回空回复
- 任何回复都不能和稳定人格参数冲突

**优先级** P0。这是基础能力，没有它"角色"这个东西不存在，后面的设计都没有附着点。

**做到什么程度算成**

- 让同一批测试者描述"它是什么性格"，描述能指向同一组维度
- 连续 3 次会话里，不出现和稳定人格参数冲突的表达

### 11.2 记忆写入与 open loop 回收（核心）

**用户得到什么** 说过的重要事情被记住，而且在合适的时候被主动提起来。

**用在什么时候** 用户提到以后会发生的事，或者讲一段情绪经历。

**流程**

```
对话结束
  → 异步抽取记忆条目
  → 置信度判断（低置信度的先放待确认）
  → 判断有没有包含以后的事 → 有就创建一个未闭合线头
  → 到时间点主动发起
  → 用户回应后标记闭合，写成共同经历
```

**规则**

- 抽取不打断对话
- 单次对话最多写入 1 到 2 条长期记忆。宁可少记，不要记错
- 未闭合线头同时最多留 3 条，多了就变回待办清单了
- 用户没有回应时不重复提醒，直接降级成普通记忆

**优先级** P0。它对应的是 H2，如果不成立，整个方案的定位就站不住。

**做到什么程度算成**

- 用户提到以后的事之后，它会在那个时间点主动开口
- 回访时，多数测试者能自己举出"它记得我"的具体例子

### 11.3 出错的时候怎么办（核心）

这一条我放在核心位置，是因为我意识到异常不是偶发情况。对这类产品来说，模型慢、记忆没命中、断网，这些是常态，而它们在什么时候发生，用户都会记住。

| 情况 | 不这么做 | 这么做 | 原因 |
|---|---|---|---|
| 模型迟迟没回 | 显示一个静止的等待 | 先做一个动作，配一句"我想想" | 静止会让人觉得它不在，动作能维持在场 |
| 记忆没有命中 | 硬编一句"我记得你……" | 改成提问 | 记错了比不记得更伤关系 |
| 断网 | 装作一切正常 | 降级成纯动作互动，并说明现在能力有限 | 它承认自己的边界，比假装完整更像一个诚实的角色 |

**优先级** P0，和 11.1 同期做。

**做到什么程度算成** 这三种情况下，访谈里没有人说"它坏掉了"或者"它变傻了"。

### 11.4 剩下的四个功能

这四个相对常规，我只写要点。

| 功能 | 用户得到什么 | 要点 | 优先级 |
|---|---|---|---|
| **记忆管理** | 知道它记住了什么，能删掉不想被记住的 | 按三类分组；每条标来源和时间；推断类的标"我猜的"；两次点击内能找到任意一条 | P1 |
| **关系记录** | 能看见关系在变化，而不是只有"聊过很多次"的感觉 | 用时间线而不是列表；主动发起的对话也要留下痕迹；空状态写"你们还没开始" | P1 |
| **成长证据** | 看到它因为自己发生了变化 | 给具体证据而不是抽象评价，比如"它开始用你的口头禅"；证据不够时写"还需要更多相处" | P2 |
| **硬件的在场行为** | 感觉到它在物理空间里，不是一个窗口 | idle 行为不依赖对话触发；动作不打断用户；离线时明确说明 | P2 |

关于成长页我想补一句：我刻意没有做等级、成就和打卡。等级会把关系变成任务，而任务是被完成、被放弃的。

关于硬件，**[后续验证]** 四个舵机加一个蜂鸣器能表达的情绪种类是有限的，需要先做一次动作和语义的映射测试。具体够不够用，我没有预判。

## 12. 四个页面

功能定义系统能做什么，页面决定用户实际看到什么。四个页面各对应一件事。

### 12.1 首页

用户打开之后第一眼应该看到什么，我按优先级排了四层：

```
第一层  它现在的状态        （趴着 / 精神 / 离线）
第二层  一句主动反馈        （基于记忆和到期的 open loop）
第三层  最近的关系变化      （一条，不是列表）
第四层  入口                （对话 / 关系记录）
```

具体大概是这样的感觉：

```
它趴在桌角，屏幕亮着。

"昨天你说今天有汇报，我猜你现在应该结束了。"

[ 聊聊 ]    [ 看看最近发生的事 ]
```

这一页我给自己定了一个要求：**用户不点任何东西，也应该已经得到了一次陪伴**。按钮是备选项，不是这一页的目的。

几种状态：有互动时显示上一次的余温，比如"刚聊完，它还挺精神"；没有互动时显示它的 idle 状态，比如"它趴着，看起来在打瞌睡"；硬件不在线时明确说"它现在不在线"，不装作在线。

我一开始在首页放了几个功能入口，后来去掉了。首页一旦变成功能面板，产品的定位就退回工具了。

### 12.2 对话页

这一页的重点是让等待也成为角色的一部分。

| 状态 | 界面表现 |
|---|---|
| 生成中 | 它在思考的表现，不用机械的进度指示 |
| 记忆命中 | 轻量提示"我想起你之前说过……" |
| 降级中 | 明确说明"我现在只能陪你待一会儿" |
| 断网 | 保留已经加载的对话，输入框置灰并说明原因 |

文本先出来，动作和表情跟着走，不等全部生成完。

### 12.3 关系记录页

用时间线，不用列表。列表适合管理数据，时间线能表达"我们之间发生过什么"。

空状态写明"你们还没开始，第一条记录会在你们第一次聊天之后出现"。每条可以展开，看到当时的对话片段。主动发起的对话也留下痕迹，用户需要知道它什么时候找过自己。

### 12.4 成长页

展示它因为用户而变化的具体证据，每条证据都能点开，跳到对应的那段对话。证据不够的时候写"还需要更多相处，它才会变得不一样"，不显示空进度条。

### 12.5 四个页面共同遵守的几条

1. 任何显示"它记住了什么"的地方，都能点进记忆详情
2. 任何主动发起的对话，都在关系记录里留下痕迹
3. 能力受限的时候明确说明，不假装完整
4. 每一屏回答的都是"它和我之间发生了什么"，而不是"这个 APP 有什么功能"

## 13. 需要记录的数据

这部分是为了让第 5 节的指标能被算出来。没有这些记录，"非任务型互动"这类判断就没有依据。

### 13.1 要存的东西

```
人格参数
  稳定参数:   { 五个维度的基准值 }
  用户影响:   { 称呼, 口头禅, 偏好话题 }
  动态关系:   { 亲密度, 共同经历数, 关系阶段, 最近情绪基调 }

记忆条目
  { id, 类别, 内容, 来源对话, 情绪标签,
    open_loop { 事件, 时间点, 是否闭合 },
    创建时间, 最近引用时间, 引用次数,
    衰减策略, 用户可见, 用户可编辑, 置信度 }
```

### 13.2 要记录的事件

| 事件 | 参数 | 能回答什么 |
|---|---|---|
| session_start | 来源：主动打开 / 通知 / 硬件触发 | 用户是自己回来的，还是被推回来的 |
| interaction_type | 任务型 / 非任务型 | 主要指标的核心分型 |
| memory_write | 类别、置信度 | 记忆系统的产出情况 |
| open_loop_created / open_loop_closed | 事件类型、间隔时长 | 这个机制有没有真的在运转 |
| memory_viewed / memory_deleted | 记忆类别 | 用户在意不在意记忆 |
| growth_evidence_viewed | 停留时长 | 成长页有没有人看 |
| downgrade_triggered | 原因：超时 / 未召回 / 离线 | 异常设计的实际发生频率 |
| dependency_signal | 回访中"想用"和"离不开"两项的自评分数 | 区分健康留存和依赖，见 5.5 |

最后两条我想说明一下为什么要埋。异常处理如果不记录，就永远不会知道有没有设计对。而依赖信号如果不测，留存数据越好看越危险。

## 14. 分阶段怎么推进

我给自己排的顺序不是按功能多少来的，是按"哪条假设最不确定、成本最高"来的。最难回退的放最后。

| 阶段 | 时间 | 要验证什么 | 产出 | 什么算通过 |
|---|---|---|---|---|
| **第一阶段 软件 Demo** | 2 周 | H2：关系感来自记忆连续，而不是回答质量 | 能跑起来的对话 + 记忆回看 + open loop 回收 | 测试者能主动说出"它记得我" |
| **第二阶段 APP 原型** | 4 周 | H1：用户要的是被动在场，而不是主动服务 | 四个页面的可交互原型 + 人格与记忆状态可视化 | 用户在没有任务的情况下主动打开 |
| **第三阶段 硬件联动** | 4 周 | H3：实体的在场感不可替代 | Otto 动作映射 + 文本与动作同步 | 去掉硬件之后，用户的主观评分明显下降 |

第一阶段我刻意不做完整功能，只做对话、记忆回看、open loop 三件事。目的是最快地知道最贵的那条假设成立不成立。

### 三个要用测试来回答的问题

| 假设 | 怎么做 | 什么情况下算不成立 | 不成立的话怎么办 |
|---|---|---|---|
| **H1** 用户要的是被动在场，不是主动服务 | 日记法 + 访谈，约 8 人，持续 2 周 | 如果用户的互动几乎都发生在有明确任务的时候 | 重心转向把回答做得更好，放弃"在场"这个核心 |
| **H2** 关系感来自记忆的连续性 | 做两个版本（有长期记忆 / 没有），同一批人各用 7 天后回访 | 如果两版在"它记得我"上没什么差别 | 把资源从记忆系统挪到对话质量 |
| **H3** 实体的在场感不可替代 | 同一个角色，手机版和桌面版做对比 | 如果用户感知不到差别 | 接受它是纯软件产品，硬件退回展示 |

### 每个阶段要交付的东西

流程图和状态表、人格参数表、记忆字段表、四个页面的原型、能跑的 Demo、小样本测试记录，以及这份文档的更新。

## 15. 关于收费，我的想法

这个阶段我不打算验证商业化，但整理竞品评论之后，有几件事我想提前定下来。因为我看到用户反感的地方大多不是"要收费"，而是"在什么位置收费"。

| 方向 | 能解决什么 | 代价和风险 |
|---|---|---|
| 卖硬件 | 一次性收入 | 规模有限。硬件本身是成本，不是关系 |
| 卖人格包 | 增加角色定制 | 会让角色变成可以买的皮肤，身份感会被削弱 |
| 云端 AI 订阅 | 覆盖模型调用成本 | 直接踩到用户最反感的那件事：核心能力被付费墙截断 |
| 卖配件 | 外观延续，给用户回来的理由 | 同类产品验证过可行，但注意力会被引开 |

把这几条放在一起之后，我给自己定了一条线：

> 收费应该买增强，不应该买"被陪着"的资格。

具体一点：更长的记忆容量、更强的模型能力、更丰富的表达方式，这些可以收费；"记得你"和"会主动找你"不行。

两个理由。一是这个品类已经被反复证明卡在留存，不是变现，在关系还没成立的时候谈付费是搞错了阶段。二是用户对"核心能力被锁在付费墙后面"的反感在评论里写得很清楚，这一步走早了会直接伤害关系本身。

成本这边我目前能想到的动作是控制结构，不是控制价格：因为角色层和生成层是分开的，模型可以换，单次对话的成本有调整空间。

**[后续验证]** 具体的硬件成本和单次对话的成本我还没算。这是这份文档里最大的空缺，见 17 节。

## 16. 有几件事我不想做

做这个方案的过程中，有几处让我不太舒服，我把它们单独写出来，因为我觉得这些是产品本身要面对的问题，不是可以绕开的。

后来查到 IEEE 正在制定一份针对人机关系的推荐实践 [文献]，把过度依恋、情感依赖、准社会关系、真实关系被替代都列成了需要处理的风险。看到之后我的想法是，这些不是我多虑，而是这个品类的固有难题。所以我给自己定了四条，每条都尽量落成一个具体的做法，而不是一句态度：

| 原则 | 具体怎么做 |
|---|---|
| **不伪装** | 首次使用就说明它是 AI。它不说自己是人，也不暗示自己有真实感受。这条也写进了 8.3 的约束里 |
| **记忆由用户控制** | 逐条可见、可编辑、可删除，不把"清除全部"当成唯一的控制方式 |
| **不用依赖换留存** | 不在用户情绪低落的时候推送；不用"你再不来我就……"这种表达；不把互动时长当目标；把"想用"而不是"离不开"当成健康信号（见 5.5） |
| **鼓励真实的关系** | 当对话涉及真实的人，引导用户去处理现实里的关系。用户这次用完就不再来，也算一次成功的使用 |

最后一条具体落到对话上是：用户说起一个真实的人，它的反应不是挽留，而是问"你打算怎么跟他说"。这句话在 8.3 的约束里也出现过，一处是原则，一处是它怎么被实现。

## 17. 还没想清楚的地方

这一节列的是我自己知道不牢的地方，也是我觉得面试时应该主动说的部分。

| 问题 | 需要谁一起 | 现在到哪一步 |
|---|---|---|
| 目标用户是不是就是"独居青年在桌前" | 用户研究 | 还是假设，要靠 3.5 的访谈替换 |
| 人格变化的速度上限 | 产品 + 数据 | 没有依据，先设一个保守值再调 |
| 主动发起的频率多少合适 | 数据 | 只能靠真实使用校准 |
| 四个舵机能表达的语义边界 | 硬件 + 设计 | 未知，需要先做映射测试 |
| 硬件成本和单次对话的模型成本 | 硬件 + 研发 | **没做**，直接影响"低成本"这个前提站不站得住 |
| 记忆抽取的置信度阈值 | 研发 | 要和工程一起定 |
| 人格测试的题目和计分方式 | 产品 + 心理学 | 框架有了，题目还没设计 |

第五项是这份文档最大的空缺。它其实不需要什么架构，一张物料清单加一份 token 成本估算就够了，但在做完之前，"低成本、可持续"只是一句话。
